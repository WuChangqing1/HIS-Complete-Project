# 系统架构、需求差异与业务状态

## 角色
ADMIN 系统管理员；REGISTRAR 挂号收费；DOCTOR 门诊医生；EXAM 检查；LAB 检验；PROCEDURE 处置；PHARMACIST 药房。服务端按照角色独立授权，前端仅负责界面可见性。

## 架构
模块化单体应用，Vue2 + Element UI + Nginx / Spring Boot 2.7 + Spring MVC + MyBatis + JdbcTemplate / MySQL 8 / Flyway。参考原要求的 MVC 三层设计；数据库高并发事务采用 Spring JDBC（部分基础数据使用 MyBatis 注解 Mapper），不额外引入微服务、消息队列。

## 与原数据库的差异
保持全部 15 张原始业务表名：employee、department、regist_level、settle_category、scheduling、register、check_request、inspection_request、disposal_request、medical_technology、medical_record、medical_record_disease、disease、prescription、drug_info。原数据库文档中多处拼写（deptment、inspection 等）沿用兼容字段。

新增 patient、prescription_item、charge_item、charge_transaction、drug_stock_transaction、auth_session、audit_log。增加的表为唯一病历号、费用状态、处方明细、库存审计、身份权限与会话所需。

`register.id` 是每次就诊的唯一 ID，`patient.case_number` 是跨就诊不变的病历号，由数据库自增 ID 格式化生成。`charge_item` 通过 `(category,ref_id)` 唯一约束区分检查、检验、处置各自 ID，防止收费项目误关联。

## 业务状态与事务
- 挂号：WAITING → IN_PROGRESS → COMPLETED；WAITING → CANCELLED（自动冲回挂号费）。
- 医技：CREATED → REGISTERED → IN_PROGRESS → COMPLETED；CREATED → CANCELLED（已缴费必须先退费）。
- 费用：UNPAID → PAID → REFUNDED；UNPAID → CANCELLED。
- 处方明细：UNPAID → PAID → DISPENSED → RETURNED → REFUNDED，或 PAID → REFUNDED。
- 并发挂号通过锁定排班记录控制号源，药房发药通过原子库存减法防止超发，金额使用数据库 DECIMAL、Java BigDecimal。
- 重要状态变更统一在事务内进行，拒绝重复执行和非法逆向跳转。

## 安全与隐私
- 密码使用 BCrypt，登录使用随机不透明 token，服务端存储 SHA-256(token)，有效期 12 小时。
- 身份证号使用 AES-256-GCM 加密、带服务端密钥的 HMAC-SHA256 指纹辅助去重；病历文字、确诊及医技结果按字段 AES-256-GCM 加密。
- 患者姓名、联系电话、住址及部分业务索引仍以可查询的明文存储；**当前版本不满足真实医疗系统的完整个人信息保护、等保或医疗行业合规要求。** 上生产前需要角色字段级授权、隐私脱敏、传输加密、审计防篡改、备份加密和安全评审。
- DATA_ENCRYPTION_KEY 与数据库备份必须配套保存，丢失或更换会导致既有加密字段无法解密。
- 单节点 session 不提供分布式会话集群；演示环境才开启 DEMO_MODE。

## 需求明确的例外
- 外部医院叫号广播系统联动，需求明确标记“本功能不完成”，故未接入。
- 实际医保结算、真实支付渠道、打印机/电子发票、国家标准临床编码及生产级报表分析需要第三方系统，不属于当前可验证演示闭环。
